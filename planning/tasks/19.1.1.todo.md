## Notes
Files edited: `crates/hydrus-core/src/solute_fortran_compat/{adapter,boundary,dual_domain,source_coupling}.rs` only (visibility in the last three, unless Q1/Q3 move a check into a kernel).
Findings: kernel `boundary::validate` is a superset of the adapter shape checks except: adapter's epsi in [0,1], |alf-(1-epsi)|<=1e-6, bottom_resistance>=0, source_tdep/source_chpar checks (adapter-only). Kernel is stricter: finiteness of all reals, material_ids/upwind lengths same, dual_porosity<=2 (same), lower code in -1..=1 and upper -2..=1, r_min>=0 and dt>0 (same), source_species 0 (same), coordinate finiteness. Adapter dt/coordinate check is identical.
`dual_domain::validate` is stricter than the adapter: requires dual_porosity in {1,2}, hydraulic_model==0, positive finite dt, finite hCritA, finite arrays, increasing coordinates, finite ParD, ParD(8)>ParD(7), ParD(2)>ParD(1), and iDualPor=2 ParD(9,10,6) bounds. Adapter currently checks only lengths, materials non-empty and material_ids range.
Order of errors may change; any test asserting a specific message gets its substring updated.

## Questions
1. Kernel `boundary::validate` additionally rejects non-finite reals and out-of-range boundary codes (lower outside -1..=1, upper outside -2..=1) that the adapter accepts today for the endpoint bundle. Per ADR-0004 this widens the rejected set. Options: (a) call it anyway, (b) call it but skip it where it would newly reject (not possible for finiteness), (c) leave endpoint checks and only delegate lengths. Which?
2. Adapter-only epsi/alf/bottom_resistance checks: move into `boundary::validate` (spec says move), which also affects direct kernel callers. OK to do so?
3. `dual_domain::validate` would newly reject requests with hydraulic_model != 0 (when no dual_domain/6-7 given), dual_porosity 0 or >2, non-finite/non-increasing values, bad ParD. Delegating is a widening. Approve (a) delegate and accept widening, or (b) keep the adapter checks and only delegate the overlapping length/material subset (not possible without a split validator)?
4. Calling `validate_uptake`/`validate_exclusion` in the adapter for bundles whose guard never fires would newly reject at request time what the kernel only rejects when called (possibly mid-run, after mutation). Confirm adding calls is wanted, and if so only when the bundle is available.
5. Do I treat each of Q1-Q4 as "skip delegation and keep adapter check" until answered?
