# 32.1.3 -- VaporWaterHeatDriver::step_atmospheric

## Notes
- The worktree is at main `3f328fc`, not `feat/met-run-path`. `planning/EXECUTION_PLAN_32.md` is absent here and was read from the main checkout (read only). The task touches only `driver.rs` and `mod.rs`, so this does not matter.
- Reference (`vapor_met.rs:584-708`) matches the spec. Differences to preserve: the predictor uses the un-clamped `step_dt` (`step()` uses `min(timestep, target - time)`; `clip_to_next_event` handles clipping inside the atmospheric step). Pass 2 reuses `local` and `input` with `upper = Atmospheric`.
- `attempt` already builds pass-2 `initial_heads = trial1 heads` and `initial_material_heads = trial1.pre_solve_heads`. The closure only supplies the solve. The pass-2 atmospheric state is the only extra, so no duplication.
- Hot-code risk: step() order of float ops is unchanged, since the extraction moves statements only. The `Inject` hooks stay in `attempt`/`commit_step` at the same points.
- Preflight vs Atmospheric (see Question 1): `validate_water_input` -> `VaporBoundaryPair::classify` rejects `(FixedHead, Atmospheric)` with `UnsupportedUpperBoundary`, and tests pin that (`mod.rs:707`, `tests/vapor_boundary_guard.rs:135`, which I may not edit). So `step_atmospheric` cannot call `preflight` as-is.
- `solve_vapor_water_trial` re-validates each decomposed Flux/Head trial (water_solver.rs:241), so the atmospheric input is validated again per trial.
- `VaporAtmosphericError` has no pass number, and neither does `Water(NonConverged)`. The spec asks for "pass number in report or error"; see Question 2.
- `VaporAtmosphericStepReport` types are reachable via `heat::vapor::driver` (a `pub mod`), so no `lib.rs` change is needed.
- No Fortran defect expected; I will mention any found.

## Questions
1. Preflight rejects `Atmospheric` (see Notes). I propose a driver-local fix in `driver.rs` only: `preflight` takes a `config` and an optional upper-substitute, and `step_atmospheric` validates with `upper` replaced by `Flux { flux: 0.0, row: zero }`, plus a finite `critical_head` check. `classify`/`validate_water_input` and the pinned tests stay unchanged, and `mod.rs` gets only `with_top_temperature`. The alternative is a new `pub(crate)` `validate_atmospheric_water_input` in `mod.rs`. OK with the driver-local one?
2. The error carries no pass number (`Atmospheric(VaporAtmosphericError)` and `Water(NonConverged)` have none). Accept that, or add a `pass: u8` field (e.g. `Atmospheric { pass, source }`)? I default to the spec shape (no pass) unless told otherwise.
