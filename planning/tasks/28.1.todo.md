## Notes
- Rust has no dtOpt: caller supplies dt each step. Vapor driver sets `local.minimum_timestep = dt` (`heat/vapor/driver.rs:391`), restarts both passes at `dt / policy.retry_factor` (`:410`), errors if `next < policy.minimum_timestep` (`:411-417`), resets the guess to old heads (`:420`). Water-only retry at `water_solver.rs:543,676`.
- Fortran: `dtOpt` only grows when `Iter <= ItMin`; WatFlow forces >= 2 iterations, so it never grows; retry sets `dtOpt = dt/3` (`WATFLOW.FOR:144-145`).
- Existing parity test uses fixed dt 0.1 (`None` schedule) or a fixed dt/3 plan for step_on (`vapor_nonuniform_parity.rs:983-990`); it stays as is.
- Public surface decision: exactly one new public function plus a small state/params struct pair is the minimum for a pure controller (state: `dt_opt`; params: dt_min, dt_max, d_mul, d_mul2, it_min, it_max). I propose one `pub struct VaporTimestepController` with one `pub fn next_dt(...)`, no config flag on `step`, default loop untouched.
- Retry granularity: dt selection only. Fortran retries per WatFlow call; Rust restarts both passes. Documented, not changed.
- dtMin clamp: Fortran clamps then fails at `dt <= dtMin`; Rust driver errors without clamping. Controller will clamp on its dt_opt; the driver error is untouched (in the step_on case 0.1/3 > 0.01, not reached).
- Single precision: Fortran dt is f32 (ten rows 0.33332E-01). Rust stays f64; step-sequence comparison needs a comparison rule for those rows without widening parity tolerances (see Q2).
- Risk: the controller sees the retry only via the accepted `report.timestep`; if the driver's report cannot supply `max(IterW, IterC)` equivalents, I will use the final-pass iteration counts (to verify in item 2).
- Risk: the step_on run under the controller may not reproduce parity rows at dt/3 exactly; the acceptance check is the step sequence, and any mismatch is reported verbatim.
