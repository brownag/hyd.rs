## Notes
- **Root cause (21.3.6, established):** `CumCh(1,1)` = 49.0625 (`42444000`) in both programs; `(man_val*1e5).round()` = `round(49062.5)` rounds half away from zero → `0.49063E+02`; gfortran prints `0.49062E+02`.
- **Pre-plan checks done in my session scratchpad (no repo state changed):**
  - Rust (`rustc 1.96.0-nightly`) `{:.Ne}` is exact-decimal and rounds exact ties to even: `49.0625@4 → 4.9062e1`, `0.125@0 → 1e-1`, `0.375@0 → 4e-1`, `0.25@0 → 2e-1`, `2.5@0 → 2e0`, `3.5@0 → 4e0`, `1.5@0 → 2e0`; carry `9.99995@4 → 1.0000e1`; precision 0 prints no `.` (`1e-1`), which the `.`-removal handles.
  - gfortran 13.3.0, same flags as `build_fortran_reference.sh`, REAL inputs: `e13.5` `49.0625 → 0.49062E+02`; `e11.1` `0.125 → 0.1E+00`, `0.375 → 0.4E+00`, `0.25 → 0.2E+00`, `2.5 → 0.2E+01`, `3.5 → 0.4E+01`, `1.5 → 0.2E+01`, `-0.5 → -0.5E+00`; `9.99995` (REAL) `→ 0.10000E+02`. These match Rust's results, so the two rounding rules agree on the cases checked. Step 6 extends this to thousands of values.
  - Prototype `.development/21.3.6/proto_fmt.patch` is the same approach and gave 41/44 combined with the vapor fixes; alone it should give 40/44.
- **Unchanged on purpose:** NaN/Infinity text, the zero branch (`-0.0` still prints ` 0.00000E+00`, as today), the `{:02}` exponent (a 3-digit exponent would print `E+100` where gfortran drops the `E`; unreachable for f32-widened values, whose decimal exponents stay within ±45 → 2 digits; out of scope), no overflow `*` fill. `format_fortran_f` already uses Rust exact formatting, so it is untouched.
