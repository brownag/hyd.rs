### Compiling foundation fields

Unless stated otherwise, scalar quantities are `f64`, node arrays have length N >= 3, face arrays have length N+1, and borrowed arrays use lifetime `'a`. All foundation types live in `vapor/mod.rs` and reference only existing Rust types.

- `VaporPrimitiveInput<'a>`: `heads`, `temperatures`, `liquid_water_contents`, `liquid_conductivities`, `liquid_capacities: &'a [f64]`; `material_indices: &'a [usize]`; `saturated_water_contents: &'a [f64]` indexed by material; `x_conv`, `t_conv: f64`. Explicit inputs prevent missing arrays from becoming zeros. Heads are the vapor evaluation `hNew`, while the supplied liquid properties may come from the source mixed-head evaluation.
- `VaporProperties`: owned `Vec<f64>` fields `liquid_conductivities`, `liquid_thermal_conductivities` (diagnostic ConLT), `vapor_head_conductivities`, `vapor_thermal_conductivities`, `vapor_contents`, `effective_hydraulic_capacities`. Thermal heat capacity is not a field of this hydraulic result.
- `VaporSourceMaterial<'a>`: `model: &'a VanGenuchtenModel`, `table: Option<&'a HydraulicTables>`. Concrete model-zero data makes source model choice explicit rather than trusting an arbitrary `dyn HydraulicModel`; `None` means direct evaluation, `Some` means the source-selected table with direct model fallback outside its source range. Later trial preflight validates consistency with the water material mapping. Actual mixed-head/table evaluation belongs to 25.4.1, not this task.
- `VaporHistoryView<'a>`: `time: f64`, `previous_timestep: Option<f64>`, `heads`, `liquid_water_contents`, `temperatures`, `vapor_contents`, `liquid_velocities`, `vapor_velocities`, `head_predictor: &'a [f64]`. `heads` is accepted physical head; predictor is separately named and never replaces old-time storage. `None` explicitly represents initialization before any previous interval.
- `VaporWaterContext<'a>`: `config: &'a VaporConfig`, `old: VaporHistoryView<'a>`, `temperature_estimate`, `initial_heads`, `initial_material_heads: &'a [f64]`, `source_materials: &'a [VaporSourceMaterial<'a>]`. `initial_heads` is independent nonlinear `hNew`; `initial_material_heads` supplies initial `hTemp`; original history is immutable across both passes and retries. Iterative hTemp updates remain internal to the trial solver.
- `VaporWaterTrial`: `candidate: WaterState`, `workspace: WaterWorkspace`, `accepted_time`, `timestep: f64`, `iterations`, `retries: usize`; owned node vectors `pre_solve_heads`, `pre_solve_liquid_water_contents`, `pre_solve_liquid_capacities`, `liquid_velocities`, `vapor_velocities`; `properties: VaporProperties`; owned face vectors `liquid_face_fluxes`, `vapor_face_fluxes`, `total_face_fluxes`. Candidate water contents hold source-corrected ThNew; pre-solve fields and properties preserve the last material evaluation. Candidate accounting represents one old-to-new interval and is never published by this report itself.
- `VaporHeatInput<'a>`: `old: VaporHistoryView<'a>`, `temperature_estimate`, `vapor_contents_new`, `vapor_velocities_new: &'a [f64]`. It accompanies unchanged `HeatTransportInput`, whose old/new water and velocity arrays remain liquid. Validation requires its old arrays/time to agree with base heat inputs; new latent heat uses the estimate, not the yet-unsolved output.

### Downstream signatures and ownership (documentation only)

These are interface contracts for later owners, not executable declarations or promised implementations in Wave 1. Module-local argument/report types below are defined by their owning task, not imported into the foundation.

- `kernels` (25.2.1): `evaluate_vapor(config: &VaporConfig, input: VaporPrimitiveInput<'_>) -> Result<VaporProperties, VaporError>` and `latent_heat(temperature: f64) -> Result<f64, VaporError>`. Latent heat returns unconverted source xLatent; heat assembly applies conversions. Preserve source one-kelvin difference, enhancement-on, and capacity multiplication by xConv.
- `water` (25.3.1): `adjust_water_rows(input: VaporWaterRowsInput<'_>) -> Result<Vec<ResetRow>, VaporError>` and `phase_fluxes(input: VaporPhaseFluxInput<'_>) -> Result<VaporPhaseFluxes, VaporError>`. Owner-local inputs carry existing liquid rows, coordinates/dt, original and current phase storage, evaluation heads/temperatures/properties, and corrected liquid storage. Results own rows or separately named liquid/vapor/total face fluxes and liquid/vapor node velocities; vapor never contributes gravity.
- `water_solver` (25.4.1), crate-private: `trial_vapor_water(state: &WaterState, workspace: &WaterWorkspace, input: WaterStepInput<'_>, policy: WaterStepPolicy, context: VaporWaterContext<'_>) -> Result<VaporWaterTrial, WaterStepError>`. Return reduced dt explicitly; never mutate accepted arguments. Keep last pre-final-solve properties and use effective hydraulic capacity for the final ThNew correction.
- `adjust` (25.3.2): `adjust_heat_rows(config: &VaporConfig, base: &HeatTransportInput<'_>, vapor: VaporHeatInput<'_>, lower: &mut [f64], diagonal: &mut [f64], upper: &mut [f64], rhs: &mut [f64]) -> Result<(), VaporError>`. Validate before publication; preserve distinct old/new latent terms and factor-two interior gradient.
- `heat::transport` (25.3.2): `solve_vapor_heat_transport(config: &VaporConfig, input: HeatTransportInput<'_>, vapor: VaporHeatInput<'_>, temp_new: &mut [f64]) -> Result<HeatTransportReport, HeatTransportError>`. Dedicated entry adds vapor after both base assembly levels and before solve; no public boolean bypass for the legacy guard.
- `state` (25.4.2): owner-local `VaporState::new(config, initial primitive/history data) -> Result<Self, VaporError>`, `history(&self) -> VaporHistoryView<'_>`, and validated trial/accept/reject methods. Initialize content and velocities through implemented kernels/phase helpers, retain predictor and previous dt separately, and expose no mutable accepted history.
- `driver` (25.5.1): owner-local `VaporWaterHeatDriver::new(validated config, column/material data, initial water/heat data) -> Result<Self, VaporDriverError>` and `step(&mut self, &mut WaterState, &mut WaterWorkspace, WaterStepInput<'_>, WaterStepPolicy) -> Result<VaporCoupledReport, VaporDriverError>`. Report owns both pass diagnostics and final phase fields. Clone candidates; restart pass one on either dt reduction; commit water/heat/vapor/workspace/time/accounting once after all checks.
- `output` (25.6.1): `observe_vapor(input: VaporObservationInput<'_>) -> Result<VaporObservation, VaporError>` recomputes the nine source observation fields from stored conductivities, final head/temperature, liquid storage/sink, and mesh; never substitutes solver velocities.
- `balance` (25.6.2): `vapor_balance(input: VaporBalanceInput<'_>) -> Result<VaporBalanceReport, VaporError>` consumes explicit old/new phase storage, temperatures, solver phase fluxes and interval; reports total-water and sensible/latent heat terms independently of observation recomputation. Existing `AcceptedWaterSnapshot.face_fluxes` remains liquid-only.
