## Notes
- Placeholder: `heat/config.rs` is one line (`//! Placeholder ...`). `heat/mod.rs` already declares `pub mod config;` and `lib.rs:10` declares `pub mod heat;`. No `lib.rs` edit needed.
- Reference pattern: `water_solver.rs:24-35` `WaterProductConfig::new(i_model, domain_count) -> Result<Self, WaterStepError>`; it calls `HydraulicModelSelector::from_i32` (`hydraulics/mod.rs:30`, returns `HydraulicError::UnsupportedSelector`) and rejects `domain_count != 1` with `UnsupportedConfiguration`. The heat config mirrors these checks without calling `WaterProductConfig::new`, so heat errors stay in `config.rs`.
- Typed-rejection pattern: `lower_boundary.rs` (`UnsupportedLowerBoundaryMode` enum, `LowerBoundaryMode::Unsupported`). Heat errors stay local to `config.rs` per spec item 2.
- Campbell convention: `heat/capacity.rs:68` uses `campbell: bool`. `HeatConfig` uses the same bool, so no integer-code error variant is needed for `iCampbell`. The `ConductivityModelNotSupported` variant is not added (instruction).
- Clippy: `too_many_arguments` fires above 7 args under `-D warnings`. A flat 10-argument `new(...)` would fail clippy. The input struct avoids this.
- Contract sign rule: source tests only the sign of `kTopT`/`kBotT` (`TEMPER.FOR:144-162`, `:87-111`). Integer codes are manual-pending (`M6_HEAT_CONTRACT.md` `## Supported`).
- `HeatCapacityZero` is not added (runtime error, not a config rejection).
- Water-side: `lTemp` is not a constructor input (see Question 2).
- Tracked convention: 202 files under `planning/tasks/` are tracked, so the task file is committed with the code.
- Risks: (a) `BoundaryKindNotSupported` is unreachable under the sign rule (Question 1). (b) Wave 2 runs 24.2.2 in parallel, but 24.2.2 needs the boundary enums that this task defines (Question 5). (c) The contract has no numeric code for `kTopT`/`kBotT`, so the enum mapping is by sign only.

## Questions
1. `BoundaryKindNotSupported { code }` cannot be reached: every nonzero `kTopT` or `kBotT` maps to a Supported sign class, and `kTopT==0` has its own variant. The contract requires one reject test per Rejected rule. Options: (a) keep the variant as a catch-all for future codes and waive its reject test, documented in the test file; (b) remove the variant. I recommend (a). Please confirm.
2. The contract's Supported table requires `lTemp=true`, but its Rejected section says `lTemp=false` is "not a rejection" (heat is off). I propose no `l_temp` input: `HeatConfig::new` is only called when heat is on, and no error variant is added. Please confirm.
3. `HeatConfig::new` takes one `HeatConfigInput` struct instead of positional arguments. Clippy `too_many_arguments` would fail `-D warnings` on a 10-argument function. Please confirm the struct shape (pub fields, no builder).
4. `iCampbell` is an input as `campbell: bool` (mirrors `capacity.rs:68`). Caller (task 24.4.x) maps the integer code 0/1; values other than 0/1 are the caller's error, not a `HeatConfigError`. Please confirm.
5. `iModel` and domain-count checks are re-implemented in `config.rs` (new variants `HydraulicModelNotSupported`, `DomainCountNotSupported`) rather than wrapping `WaterStepError`. Also the boundary enums (`TopBoundaryKind`, `BottomBoundaryKind`) live in `config.rs` per the plan's "validated boundary kind", which makes task 24.2.2 (Wave 2, parallel) depend on 24.2.1 at compile time. Option: move the enums to `boundary.rs` owned by 24.2.2. Please choose.
