# 25.5.1 — Atomic two-pass coupled driver
## Goal
Implement `V/driver.rs` as a vapor-aware driver that runs the two source-ordered water->velocity->heat passes from one old snapshot on cloned local candidates and commits water, heat, vapor history, predictor, time and accounting exactly once.

Constraints/risks:
1. Trial candidate's `accounting` is not advanced by the trial (only the legacy path increments); the driver must do it.
2. Integration tests see only the public API; `solve_vapor_water_trial` is crate-private, so injecting a failure after pass-2 water/heat/diagnostics may need inline tests in `driver.rs` or natural inputs (non-finite heat parameter, singular pivot, NaN boundary).
3. Predictor boundary nodes: source excludes Dirichlet end nodes (`iBot/iTop` by `KodBot/KodTop`); mapping from `LowerBoundaryMode`/`UpperBoundary` needs confirmation (Q3).
4. `#[allow(dead_code)]` on the trial becomes stale; clippy does not fail on stale allow, left untouched.
5. f64 only, no reference comparison, no new dependencies.

Approved answers: Q1 pass-2 initial_heads=pass-1 candidate heads, hTemp=pass-1 pre_solve_heads (WATFLOW.FOR:94-96). Q2 steps+1, iterations=pass1+pass2, storage/boundary/sink totals unchanged. Q3 exclude fixed-head ends (iBot/iTop). Q4 temperatures only in VaporState.
Correction A (WATFLOW.FOR:136-149): source reset on dt cut is hNew=hTemp=hOld, TempN=TempO, dt/3, iTemp=0; trial-internal retry would reuse predictor/pass-1 temps, so driver owns retries. Correction B (HYDRUS.FOR:650-662,695): predictor stored at commit with unit ratio, rescaled at next step by dt_attempt/previous_timestep.

## Questions

2. Accounting: trial gives no `WaterBalance`. Increment only `accepted_steps` and `cumulative_iterations` (iterations = sum of both passes or pass-2 only?) and leave storage/boundary/sink totals unchanged, or should I derive them from trial diagnostics? Default: steps +1, iterations = pass-1 + pass-2, others unchanged and flagged in report.
3. Predictor: apply the extrapolation to all nodes, or exclude end nodes fixed by Dirichlet boundary (derive from `lower`/`upper`)? Default: exclude fixed-head ends per source `iBot/iTop`.
4. Is it acceptable to hold accepted temperatures only in `VaporState` and not in a parallel `HeatState`? Default: yes.
