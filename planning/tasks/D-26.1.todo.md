### Test harness (important)
- Vapor-OFF controls run the legacy `HeatWaterDriver` (`crates/hydrus-core/tests/vapor_heat_boundary_parity.rs` in 6959c0b, lines ~899-935). Vapor-ON runs use `VaporWaterHeatDriver` (lines ~961-). The vapor-off match therefore does not test the vapor driver's predictor, initialization (`initialization_timestep`, `initial_head_predictor`), or pass structure. "Vapor-off is correct" (orchestrator H2 premise) is only partly supported.
- Fortran compile flags: `-std=legacy -ffixed-line-length-none` (no `-fdefault-real-8`), so implicit REAL locals in `ConVapor`/`VaporContent` are single precision.
- Fixture BC pairs (`expected_codes`): FD = (kTopT -1 flux, kBotT 1 Dirichlet temp); FF = (-1, -1); FZ = (-1, 0) passes; DF = (1, -1) passes. Drift appears only where top is flux and bottom is not zero-flux, but FZ and DF both pass, so the BC pairing alone does not explain the pattern.

### Hypothesis ranking (current)
1. Driver machinery or vapor-only terms in the vapor path (this is the decisive split). Closest to H2 as written. Static reading finds no vapor term that differs from Fortran in the head solve. The main untested difference is that vapor-on and vapor-off use different drivers. Settled by step 1 (and step 6 for onset). Prior: highest.
2. H1, time level. The Rust two-pass structure matches Fortran (`HYDRUS.FOR:402-497`), and `TempN`/`ThVNew` levels match on reading. Residual risk is the pre-solve vs post-solve vapor content on commit. Settled by steps 2-3. Prior: medium-low. Only a change of more than 1e-3 cm would make it the cause.
3. H3, single precision. Fortran locals in `ConVapor`/`VaporContent` are REAL*4. Relative error ~1e-7 per term. Growth to 5.7 cm would need strong amplification, which is unlikely. Settled by step 4. Prior: low.
4. H4 (new), boundary-row vapor terms. Affects boundary velocities (`v_liquid` at ends), not interior head, given head-type BCs. Settled by step 5. Prior: low for head, but relevant to the `v_liquid` failure.
