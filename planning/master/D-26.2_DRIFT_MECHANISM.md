# D-26.2 vapor-on head drift: mechanism (orchestration 26 drift check)

Date: 2026-11-13. Plan: [TODO_26_DRIFT.md](../TODO_26_DRIFT.md). Branch: `orchestration/26-drift` from `feat/heat1` (`71ba3d3`).
Scope: prove the mechanism of the FD/FF vapor-on head drift (acceptance exception 1). No change to `src/`, `src_reference/`, fixtures, criteria, or the acceptance decision.

## Verdict

**Proven: the drift is single-precision (REAL*4) arithmetic inside the pinned reference's vapor-coupled solve.** The Rust driver (double precision) agrees with the same Fortran source built with `real*8` defaults to the printed precision of the outputs, and the reference's single-precision fixture differs from that double build by exactly the Rust-versus-fixture drift.

The Rust driver is not the source of the drift.

**Not proven:** which REAL declaration(s) amplify the rounding error. This check shows the amplification comes from the single-precision reference arithmetic. It does not isolate the variable(s).

## Evidence

All numbers are for `vapor_heatbc_fd_on` unless marked FF. Rust = `.development/26.4.1/attempt-20261113T054631Z` candidate (main repo, `71ba3d3` code) and the scratch Rust dump on this branch.

1. **Instrumentation is inert.** The instrumented single-precision Fortran (dump flag off) reproduces the committed fixture exactly at printed precision: head and temperature differences are 0.0.
2. **Same-input first divergence (single precision).** At step 1 (t=0.1), the old temperatures are identical (6, 7, 8, 9 °C). Pass-one temperatures agree (6.00695 vs 6.00695). The pass-one head at node 2 differs by 2.8e-3 cm (Fortran −9988.7588, Rust −9988.7560). Pass-two head differs by 4.2e-3 cm.
3. **Growth.** Committed head difference (max over nodes 2–5): 4e-3 cm at step 1, 1.2e-2 cm at step 2, 0.1 cm at t≈76, 1.0 cm at t≈151, 4.3 cm at t=240. Growth is gradual, with no single jump.
4. **Double-precision Fortran (same source, `-fdefault-real-8 -fdefault-double-8`).**
   - FD: Rust minus double-Fortran head is at most **5.0e-9 cm** at every one of the 2399 committed steps. Temperature is at most **5.0e-10 °C** at every step.
   - FF: Rust minus double-Fortran head is at most 5.0e-4 cm, which is the printed resolution (`f11.3`).
5. **The fixture is the single-precision build's output.** Double-Fortran minus the FD fixture head is **5.704 cm at t=240**, which is the Rust-versus-fixture drift. For the vapor-off control, double and single agree at printed precision, so the effect is confined to the vapor-coupled path.
6. **The FD `v_liquid` exception has the same cause.** At node 37, t=240: Rust 4.155811e-09, double Fortran 4.1558e-09 (|Δ| = 1e-14), single fixture 3.6301e-09 (|Δ| = 5.26e-10, which is the 1.50× failure against bound 3.50e-10). Max over all nodes at t=240: Rust vs double 3.6e-12; Rust vs single 5.3e-10.

## What this means for the acceptance

- Exception 1 (FD head drift and `v_liquid` row) is a **reference-precision effect**, not a Rust defect. It falls in the H7 precision class.
- The frozen criteria v3 are unchanged. The `v_liquid` bound was not widened.
- The FD and FF acceptance decision (accepted with exceptions, 2026-11-13) now has a stated cause. The cause is the fixture's precision, not an unexplained physical mismatch.
- A decision is still needed on how to record this. The choices, none made here, are:
  (a) keep the single-precision fixtures as the reference and record the FD `v_liquid` row and the head drift as an explicit H7 precision exception;
  (b) add a double-precision reference evidence class, which would be a new producer build and new fixtures, then re-run the comparison under a separate criteria decision.

## Corrections to earlier notes

- The D-26.1 diagnosis note said single precision was ruled out because an f32 kernel change moved the t=240 error by about 0.02 cm. That test rounded Rust kernel outputs. It did not change the Fortran arithmetic, so it did not test the reference's REAL*4 solve. The conclusion there was wrong for the reference.
- The M3 probes (`planning/STATE_26.md`, 2026-11-13) rounded Rust storage (heads, heat temperatures, vapor velocities) to f32. Those probes correctly show that storage rounding on the Rust side is not the cause, but they did not test the single-precision solve in the reference, which is the actual cause.

## Method

- Scratch Fortran: `.development/26-drift/fortran-ref` (single precision, dump instrumentation in a new `DUMPDRF.FOR` and three calls in `HYDRUS.FOR`) and `.development/26-drift/fortran-ref-dbl` (same source, `-fdefault-real-8 -fdefault-double-8`, built manually with gfortran).
- Scratch Rust: `.development/26-drift/rust-wt`, env-gated dump in `heat/vapor/driver.rs` at the step commit. The dump was verified inert (identical HELD lines with and without it). Per-case dump files `.development/26-drift/rust-<case>-v2.txt`.
- Pairing: Fortran `tag 3` row *i* with Rust committed row *i*. The Fortran tag-3 time label is the end of the step, one step ahead of the state it records, and the Fortran single-precision clock drifts from Rust's exact clock, so pairing by printed time is wrong. The Fortran dump has no tag-3 row for step 1.
- Scratch outputs are under `.development/` and are not committed.

## Not done

- A Rust-side scratch test copying the Fortran single-precision values into Rust (plan task 6 as written). The double-precision build is a stronger test, so it replaces that step.
