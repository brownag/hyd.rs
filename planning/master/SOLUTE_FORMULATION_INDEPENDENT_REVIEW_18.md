# Independent review: solute formulation and the pinned-Fortran objective

**Scope.** Read-only review of whether there is a defensible mathematical or scientific reason to retain Rust’s bespoke finite-volume/backward-Euler (FV/BE) solute scheme as the target when the project objective is emulation of the pinned Fortran behavior. This review does not select or implement a discretization. No build, test, or solver was run.

## Finding

There is a sound mathematical reason to use a conservative FV spatial balance and backward Euler as a *numerical method for the specified continuum equations*: internal face fluxes cancel between adjacent control volumes, and backward Euler is A-stable for the linear stable modes to which that result applies. Those are useful design properties. They do **not** establish that this particular implementation is accurate, positivity-preserving, physically validated, or compatible with HYDRUS’s pinned discrete behavior. Nor do they make FV/BE the right emulation target.

On the premise in the question—emulate the pinned program—the existing evidence does not justify retaining FV/BE *instead of* emulating Fortran. The repo’s initial compatibility decision explicitly names the hash-pinned source snapshot as the numerical reference for the selected subset (`planning/INITIAL_PROMPT.md`, “Compatibility target and scope decision,” lines 6–11). In that objective, a different discretization can be a useful independent implementation or cross-check, but not a substitute for compatibility unless the project owner explicitly changes that objective. The exact compatibility claim still needs a bounded subset/configuration and observable/precision contract; this is not a claim of full HYDRUS release parity.

The contrary conclusion is also not supported: the pinned Fortran scheme is not thereby proven more accurate or physically correct. Retained mathematical evidence is mixed by case, one-mesh/one-timestep component evidence is not an accuracy verdict, and the Example 3 solver comparison to its independent finite-domain reference remains unmet. The narrow next step is therefore a bounded **requirements reconciliation**: confirm whether the initial pinned-source numerical-reference decision remains controlling for the selected solute subset, and name that subset and compatibility observables. Do not launch a scheme change from this review alone.

## What the repository specifies and implements

### Requirements and project objective

- **Repo-level compatibility objective (fact):** `planning/INITIAL_PROMPT.md` lines 4–11 frames the work as a Rust port of a defined subset and says the hash-pinned source is the numerical reference; it calls for both compiled-source comparison and independent checks. It also limits the claim: exact HYDRUS release identity is unverified and full product parity is not promised.
- **Historical narrower task scope (fact):** `planning/EXECUTION_PLAN_10.md` lines 12 and 94, and `planning/tasks/10.3.1.todo.md` lines 3–22, implemented one conservative in-memory solute step, expressly excluded Fortran parity claims at that stage, and said no manual expected output was available. That explains the original design choice; it does not supersede the broader stated project objective by itself.
- **Normative mathematical model (fact):** `planning/master/SOLUTE_VERIFICATION_SPEC.md`, “Equation, dimensions and signs,” lines 58–103, specifies constant-water, linear-equilibrium storage `a_j=theta+rho Kd_j`, flux `J=qC-theta D C_s`, the continuum transport/ordered-chain equations, inward inlet flux, zero-gradient outlet, and independent mass/flux/reaction observables. It specifies the continuum problem, not a mandatory Rust stencil or time integrator. Sections “Finite diffusion benchmark” (133–144), “Scalar finite-domain inlet/outlet benchmark” (146–167), and “Actual finite Example 3 chain” (169–220) supply independent test problems.
- **Rust implementation (fact):** `crates/hydrus-core/src/solute.rs`, `assemble_flux_operator` (1299–1325), constructs signed upwind advective and dispersive face fluxes and adds each face’s contribution with opposite signs to neighboring rows. `control_volume_width` (1451–1458) uses half endpoint cells and centered nodal widths. The step path uses implicit endpoint-time storage; the source history and description are summarized in `planning/master/SOLUTE_RUST_FORMULATION_17.md`, “Transport and storage rows” and “Time and endpoint treatment” (20–36). `apply_endpoint_boundary_rows` (1328–1358) supports concentration, total-flux, and advective-outflow modes; these are not uniformly the Fortran endpoint equations. Reactions/sorption are implemented in the process path, with one kinetic pool and ordered species coupling (Rust formulation report, 26–30).
- **Fortran implementation (fact):** `src_reference/SOLUTE.FOR`: `Solute` invokes `Coeff`, `MatSet`, then `BanSol` over two levels (`SOLUTE.FOR` 35–37, 106–144); the header calls the method “Mass-lumping finite elements” (3–4). `MatSet` constructs element-based tridiagonal rows and boundary branches (755–927); `epsi`/`alf` and level-dependent terms occur in assembly (35–37, 830–864); `Disper` is mode-dependent (1025–1068). As detailed in `SOLUTE_FORTRAN_FORMULATION_17.md`, this is not the Rust face-flux/control-volume operator. The exact contribution of every switch is configuration-specific.

“Conservative” is also not shorthand for “accurate”: it describes a discrete balance property. “Backward Euler” is not shorthand for “unconditionally correct”: A-stability for linear stable modes does not guarantee spatial accuracy, positivity, boundary fidelity, nonlinear convergence, or correct physics.

## What the retained numbers do—and do not—say

### Orchestration 16: compatibility divergence, not a scientific ranking

- **Diffusion, measured:** On the 65-node first-step trace, all 63 interior rows differ by `(1.37599995327, -2.75199926758, 1.37599995327)` in physical lower/diagonal/upper coefficients; the outlet rows differ too. Maximum state difference is `0.0003047828` at the outlet (`SOLUTE_DIFFUSION_NORMALIZED_TRACE.md`, summarized in `SOLUTE_FORTRAN_FORMULATION_17.md` 50–53 and `STATE_16.md` 45–50). This establishes different operators, not a required target or error ranking.
- **Scalar Robin, measured:** At the midpoint, Fortran is `(-13.86759472, 30.10119629, -13.65259457; 1.96497154)` and Rust `(-27.95, 58.05201562, -27.52; 1.96529857)`; the sampled outlet closures differ (`SOLUTE_ROBIN_NORMALIZED_ROWS.md` 17–32). No single-factor counterfactual isolates FE/FV, weighting, or endpoint effects.
- **Reaction, measured:** In `reaction_equal`, Rust S1 is `0.9937888199` versus Fortran’s printed `0.993769467`; the inactive `reaction_zero` control agrees in the tested values. The available Fortran row has neighbor coupling, but a complete common-basis element/storage/reaction ledger is absent (`SOLUTE_REACTION_NORMALIZED_EQUATIONS.md` 40–79; `SOLUTE_FORMULATION_DECISION_17.md` 18–31). This neither proves the Fortran reaction treatment is right nor locates a Rust defect.
- **Example 3, measured:** First-interval rows differ at sampled inlet/midpoint/outlet locations for three species, and the Fortran outlet row is `(1,-1,0;0)` after orientation conversion. It is a derived fixture, not a recovered manual deck; this trace is not an analytical oracle (`SOLUTE_EXAMPLE3_NORMALIZED_TRACE.md` 23–63).

Thus Orchestration 16 answers **why the rows/results can differ**: they are distinct schemes and endpoint treatments. It does not answer which scheme meets the repo’s compatibility objective, and its `no_fix_cause_unisolated` disposition means no localized bug was proven—not that the Rust scheme was scientifically preferred.

### Independent continuum measurements: genuine evidence, bounded conclusion

`SOLUTE_ANALYTICAL_EVIDENCE.md` reports that, at its tested mesh and timestep, Rust’s diffusion-cosine maximum concentration error is `1.1128466e-05`, while Fortran’s is `0.0031359326` (lines 68–73); Rust’s final total-inventory error is `3.8191672e-14`, versus Fortran’s `0.0009916875` (99–100). That is real evidence favoring the tested Rust result for that case/configuration against that admitted continuum reference. It is not proof FV/BE is generally more accurate, nor proof that Fortran must not be emulated.

The same component evidence points the other way on reactions: Rust’s `reaction_equal` S1 profile error is `0.0011200574`, versus Fortran’s `3.0753078e-05`; Rust S2 is `0.0026844201`, versus Fortran’s `4.3963171e-05` (80–85). For `scalar_robin`, Rust’s maximum L-infinity error is `0.00053788583`, Fortran’s `0.00068353907` (92–93), a smaller separation. The report explicitly limits all these results to one mesh/timestep and states that thresholds, controlled convergence, and solver accuracy acceptance are absent (7, 122–130). These are case-bounded measurements—not a scientific warrant to retain one scheme across the selected subset.

The later convergence wave does not close that gap: only 32/57 authorized convergence starts ran; the matrix stopped at a storage ceiling; no fitted order, solver threshold, or accuracy acceptance was reported (`SOLUTE_CONVERGENCE_EVIDENCE.md` 3–7, 17–30, 38–47). Its inability to continue is an operational limitation, not evidence for either scheme.

## Independent scrutiny of Orchestration 17’s memo

The prior memo is appropriately cautious that FV/BE history is not a target decision, parity is not physical truth, and the row traces do not identify a Rust defect (`SOLUTE_FORMULATION_DECISION_17.md` 12–31, 56–60). Two qualifications are needed for the question now posed:

1. **The framing understates the existing compatibility directive.** The memo presents “retain FV/BE,” “target Fortran,” and “defer” as peer options and says the evidence does not establish whether Fortran behavior is the required target (lines 33–62). That is accurate if considering only Orchestration 10’s earlier solute-task scope and the immediate Orchestration 17 user request. It is incomplete against `INITIAL_PROMPT.md` lines 6–11, which already selects the pinned snapshot as numerical reference for the defined subset. The remaining legitimate uncertainty is the exact subset/compatibility contract and whether a later explicit decision superseded that directive—not an absence of any project-level compatibility objective. The review does not infer from the prompt that every Fortran branch or all release outputs must be copied.
2. **“Independent validation absent” needs temporal and claim precision.** Phase 5 handoff gaps were real, but later `SOLUTE_ANALYTICAL_EVIDENCE.md` admits component references and records measured Rust/Fortran errors; its corresponding `SOLUTE_CONVERGENCE_EVIDENCE.md` also records incomplete follow-up. So it is too broad to say there is no independent analytical evidence. There *is* independent mathematical benchmark evidence; what remains absent is accepted accuracy, controlled convergence/error bounds for the required coverage, a completed Example 3 solver comparison, and physical validation. The decision memo cites the Phase 5-era gap, rather than synthesizing those later reports.

This correction changes the strength of the conclusion, not the scientific boundary: analytic component results inform method performance on covered cases; they do not displace the compatibility requirement or establish physical validity.

## What could justify FV/BE, and what is missing

**Defensible reasons to keep it as a method/secondary implementation:** telescoping internal face fluxes suit local conservation; backward Euler can be useful for stiff transient integration; the source is an explicit in-memory Rust contract with caller-owned water and transactional state; and the independent diffusion measurement is favorable at its tested resolution. Those support retaining it as an engineering option, a separately named mode/API, or an independent cross-check if the project owner wants that scope.

**Not established:** that the scheme is more accurate over the selected solute physics; that it meets a useful order/rate as mesh and time step refine; that it preserves nonnegativity for all supported coefficient/boundary cases; that its boundary and reaction discretizations implement all required continuum terms consistently; that its present choices are necessary for conservation/stability; or that it matches the pinned source. No retained scientific result supplies those general conclusions.

If the target is emulation, mathematical elegance is not a reason to substitute FV/BE for the target’s discrete behavior. An emulation may intentionally reproduce a numerically inferior or historically idiosyncratic algorithm; independent verification should report that limitation rather than silently “correct” it. Conversely, a distinct FV/BE implementation can be scientifically justified for an independent solver objective, but that is a different requirement and needs acceptance evidence tailored to it.

## Bounded next step

The user has confirmed that emulating Fortran has been the project objective throughout. Combined with `INITIAL_PROMPT.md`'s pinned-source numerical-reference decision, this resolves the target question: **For the selected solute subset, compatibility with the pinned Fortran behavior is the goal.** No further target-selection question is needed.

The evidence does not justify the bespoke FV/BE scheme as a replacement for that compatibility target. Its conservation/stability properties and favorable diffusion result at one tested resolution may justify keeping it as a separately scoped independent solver or cross-check, but not silently substituting it for emulation. This review does not recommend deleting existing Rust code or claim Fortran is physically correct.

The next planning step, before numerical edits, is to define the bounded compatibility contract: selected Fortran configurations/switches, mapped inputs and outputs, observable locations/times, precision and tolerances, plus unsupported modes. Existing Orchestration 16 traces already establish that current FV/BE rows are not emulation. Then a separate implementation plan can scope the smallest changes needed to match the pinned behavior and validate them against independent mathematical evidence without conflating parity and accuracy.
